Multi-Cloud Storage with Blockchain Support

One storage tier split across three providers — Backblaze B2, Tigris, and Cloudflare R2 — with a Python/Flask daemon that routes files, verifies integrity, and writes tamper-evident receipts to a multichain blockchain. A copy of the storage and audit page for the Project Repo.

Series: Project Repo Focus: Multi-cloud storage and integrity Status: Architecture defined · daemon drafting

1. Architecture: three providers, one daemon, one ledger

The storage layer is a federation of three object stores, each chosen for a different trade-off: Backblaze B2 for cheap, durable, long-term cold storage; Tigris for open-source, serverless auto-ingest and lifecycle management; and Cloudflare R2 for low-latency edges and built-in CDN. A single Python daemon sits in front of all three, presenting one upload/download API. It shards each object, writes it to all three stores with checksums, and records a provenance receipt on the blockchain.

Backblaze B2
Cold archive, ~1 TB bucket, versioned, cheapest long-term
Tigris
Open-source S3-compatible, auto-ingest, lifecycle policy
Cloudflare R2
Edge-low latency, CDN-ready, no egress fees

3. Python daemon using Flask

The orchestration daemon is a Python Flask application. It owns the upload/download endpoints, the object split (chunked into shard files), the checksum computation, and the blockchain emission loop. The Flask app is the single control plane: all three storage clients hand off their byte ranges to the daemon, which reassembles and records.

4. Multichain blockchain for tamper-evident receipts

Every upload ends with a cryptographic receipt on-chain. The daemon emits a single transaction containing: the object digest, the provider mapping, the timestamp, and a per-provider shard hash. By writing to three chains, the system gains a multichain anchor: an attacker who rewrites one chain cannot rewrite the set without consensus. The receipt table is stored in SQLite, indexed by object digest, so on-chain and off-chain data stay reconcileable.

Multichain layers

  • MultiChain — a permissioned, multi-org blockchain platform; low-fee, private, deterministic
  • Native assets — use MultiChain's built-in issuance for token-bound receipts
  • SQLite index — local reconcile table for off-chain receipt lookup

5. Storage / file manager (lazy-loading hub)

The daemon exposes a file manager that is a lazy-loading tree, backed by SQLite. The parent object row is fetched eagerly; shard rows are fetched on demand when the client expands a file. Each row carries size, checksum, and provider location, and the SQLite hub is the single source of truth between the file manager, the daemon, and the blockchain sync job.

6. Event viewer & sync

The event viewer aggregates daemon logs, sync events, and checksum mismatches into a chronological feed. Each event references a session, an upload, and a provider, and the viewer renders them as a compact timeline with severity color-coding. Missing or mismatched shards are flagged as warnings, so an operator sees drift before it becomes a loss.

Event feed columns

  • Session / upload / timestamp
  • Type: upload, sync, checksum, warning, error
  • Severity: info, warning, alert
  • Provider report + link to SQLite event row
