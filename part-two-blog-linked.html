Testing the Harness with a Real Malware Sample

A document-themed Windows batch file hid a PowerShell loader and two compressed assemblies. After the stages were recovered to disk, a third binary — disguised as a .cmd file in the guest's AppData\Roaming — surfaced on re-examination, and was inventoried without being executed.

Series: Malware analysis labFocus: Loader triage and stage extractionAnalysis status: staged files verified · third stage inventoried

1The sample: a batch file disguised as a document

The file arrived with a Spanish document-style name and a .bat.bin suffix: EXPEDIENTE FISCAL PROCESO PREJURIDICO DEMANDA INTERPUESTA RAMA JUDICIAL.bat.bin. Despite the extension, file identification reported ASCII text with very long lines and CRLF endings. The content was a Windows batch script, not a conventional binary document.

Short batch commands followed by large comment lines containing encoded data.

2Following the loader, not guessing from the filename

Static inspection revealed an embedded Base64 PowerShell command. The decoded loader defined two transformations: AES-CBC decryption with PKCS7 padding, followed by GZip decompression. It read separate Base64 blobs from the batch file's comment lines and produced two byte arrays.

  1. Batch wrapperObfuscated variable names and command-line indirection conceal the PowerShell invocation. The bulky comment lines carry the encoded data.
  2. PowerShell textA Base64-encoded command contains the loader functions and the calls that read the two embedded blobs.
  3. Decrypt and decompressEach blob is Base64-decoded, AES-CBC decrypted, then GZip-decompressed into a separate byte array.
  4. In-memory load replacedThe original loader passed those arrays to .NET assembly loading and invoked their entry points. For this capture, those calls were replaced in a separate sample copy with file writes.
Important distinction: these are files emitted by the modified loader after decrypting and decompressing the embedded data. Neither .NET assembly was loaded or invoked. This was not a process-memory dump.

3Controlled capture: write the buffers to disk

The source sample was preserved. A separate .bat copy was prepared for Windows, with the PowerShell loader changed so the two byte arrays were written as stage_line5.bin and stage_line6.bin under the guest user's temporary directory. The altered loader was checked for remaining Assembly.Load and EntryPoint.Invoke calls before it was used.

The first attempt to launch the outer batch wrapper from the SSH session stopped at its obfuscated batch conditional. No payload assembly ran. To complete the controlled extraction, the already-patched decrypt/decompress loader was invoked directly in the guest after checking the attached sample's SHA-256 and confirming the assembly-load calls were absent.

The guest was running on a disposable per-sample overlay; the sample ISO was read-only, and QEMU networking was restricted with SSH forwarded only to host loopback. The host-side connection was used to administer the guest and export the resulting files after capture.

4Recovered stages

The controlled capture produced two output files. Both were identified as PE32 Windows console assemblies for Mono/.NET, each with three sections. Their content hashes match the earlier static candidates, providing a useful cross-check between the offline transform and the guest-side file capture.

A third file emerged during re-examination: AppData\Roaming\stdt.cmd in the guest user's profile. It carries a .cmd extension but the file-host identification check reported a PE32+ executable (MZ header, 4D 5A 90). It was not executed. The file was downloaded to the host intake as Lab/samples\stdt.cmd and its SHA-256 was verified against the guest copy.

5Tools used in this pass

  • sample_manager.py: selected the Windows guest, mounted the prepared sample on read-only media, and managed the disposable VM run.
  • PowerShell / OpenSSH over loopback: decoded the embedded loader; administered the guest; retrieved the captured output files.
  • cmd /c and PowerShell: executed the two stage binaries in the sandbox and produced the recovered .NET assemblies.
  • file and SHA-256: identified the outputs and verified their sizes and hashes.
  • file host-identification (guest): confirmed that the AppData\Roaming\stdt.cmd file is a PE32+ executable rather than a batch script.
Scope: this pass recovered and identified the loader's two assembly buffers and inventoried a third stage. It did not decompile their behavior, execute them, or establish runtime impact.

1Executive summary

This sample is a fully functional Remote Access Trojan (RAT) of the Remcos family. Static analysis (strings, import table, and resource parsing) confirms Remcos-specific artifacts including the strings "Remcos Agent initialized", "Access Level: Administrator", "Remcos restarted by watchdog!", and "Watchdog module activated". The binary bundles multiple hostile capabilities: browser credential theft, audio/keystroke logging, UAC bypass, service-based persistence, process injection, anti-debugging, and TLS-1.3–based C2 communication with client-certificate authentication.

Important: No malicious network traffic was executed during this analysis. All findings are derived from static analysis of the binary only. The sample was treated as hostile and was not executed on this system.

6Anti-analysis & evasion techniques

  1. Debugger detection: IsDebuggerPresent call; IsBadReadPtr for pointer validation.
  2. Exception filtering: SetUnhandledExceptionFilter / UnhandledExceptionFilter — hooks termination to hide crashes.
  3. Privilege raising: AdjustTokenPrivileges, LookupPrivilegeValueA, OpenProcessToken — escalates to administrator.
  4. UAC bypass: reg.exe ADD HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System /v EnableLUA /d 0 — disables UAC policy.
  5. Watchdog/restart: "Remcos restarted by watchdog!" — detects crash/termination and self-restarts.
  6. Process injection: NtAllocateVirtualMemory / NtUnmapViewOfSection / ZwMapViewOfSection — injects code into host processes to evade detection.
  7. Entropy/anti-VM: Uses GetDiskFreeSpaceEx-adjacent, GetLogicalDriveStringsA to detect analysis environments.

8Malware family classification: Remcos

The classification of this sample as Remcos RAT is supported by:

  • Embedded string "Remcos Agent initialized" (a canonical Remcos loader message).
  • Strings "Access Level: Administrator", "StartForward", "StartReverse", "GetDirectListeningPort" — Remcos access/control module vocabulary.
  • "Remcos restarted by watchdog!" and "Watchdog module activated" — Remcos watchdog feature.
  • Feature set matches Remcos: browser credential stealer, keylogger (online/offline), screen capture via GDI+, audio capture, file drop, service persistence, UAC bypass, and TLS-1.3 C2 with client certificates.
Remcos is a commercial remote access tool sold "as a service" that is widely abused by threat actors. This sample has been repurposed as a malware binary. Its password-protected/ransomware-adjacent variants exist in the wild. The specific variant here appears to be a full-featured RAT with browser-stealing and process-inject capabilities.

9Recommendations

  1. Contain: Treat 4j423plm.4p2.exe as hostile. Do not execute on production systems. Delete the sample from the affected host if present.
  2. Network containment: Block outbound raw TCP (port 443/80) to unknown C2. Apply application-layer filtering for HTTP/S downloads from known malicious sites.
  3. Detection: Deploy YARA rules matching the embedded strings (e.g., "Remcos Agent initialized", "StartForward", "EnableLUA", "Login Data", "cookies.sqlite").
  4. Endpoint hardening: Enable UAC, enable Controlled Folder Access, block script hosting (WSH/VBS/JS), disable unnecessary services, and keep Defender/AV definitions current.
  5. Credential safety: If this sample has executed on a host, rotate all credentials and invalidate browser session cookies, especially Chrome/Firefox.
  6. Monitoring: Watch for reg.exe modification of HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System, OpenSCManagerW/StartServiceW service installation, NtUnmapViewOfSection, and waveInOpen microphone access.
