Building an Isolated Malware-Triage Lab

Part one documents the lab’s operating model: stage one sample, inspect it in a disposable guest, return a report, and reset before the next run.

Series: Malware analysis labFocus: Architecture and first validation

The architecture: host orchestrates, guest inspects

The lab separates control from analysis. The sample manager and triage agent run on the host; REMnux and Windows are disposable workspaces. The agent is not installed inside either VM and the private SSH key stays on the host.

The analysis transport differs by guest: Linux input and reports use the 9p share; Windows input is a read-only ISO, and the host-side agent writes its report to the configured host path watched by the manager. In both cases, SSH is the management channel—not a route for the sample to reach the network.

These guests are egress-restricted rather than literally network-free: QEMU uses restricted user networking, and SSH forwards bind only to host loopback (REMnux on port 2222; Windows on 2223). This preserves a narrow management path without giving the sample an ordinary Internet route.

Technologies and the isolation boundary

Python manager + SQLite
Runs the queue, selects one sample, records its hash, watches for the matching report, and tracks completed samples.
QEMU/KVM + qcow2
Runs the guests with hardware virtualization. A per-sample qcow2 overlay captures writes; the installed base image remains the clean starting point.
REMnux + Windows 11
Prebuilt Linux and Windows analysis guests are selected according to the sample, rather than building a new OS for every run.
Restricted QEMU networking
restrict=on blocks ordinary guest egress. SSH forwards bind to 127.0.0.1, exposing the management channel only on the host.
OpenSSH + host key agent
The host-side agent connects for bounded inspection. The private key stays on the host; it is not copied into the malware VM.
Virtio-9p + read-only ISO
Linux uses a shared host/guest mount for sample and report exchange. Windows receives the sample on read-only media; its report is written to the manager’s watched host path.
Air-gap terminology: this is an egress-blocked, host-managed lab—not a literal no-network air gap—because the host retains a loopback-only SSH forward. A stricter no-NIC profile would remove SSH and use offline media for all transfers.

One run, from queue to clean state

  1. Identify and stageThe manager selects one file from the host collection, calculates its SHA-256, skips hashes already completed in its SQLite ledger, and records the expected report location. It stages only that sample for the current run.
  2. Create a disposable workspaceThe guest starts from a new hash-named qcow2 overlay. Writes made during analysis land in that overlay, leaving the installed base image available for later runs.
  3. Deliver through a controlled pathLinux samples and reports use the manager’s 9p shared mount. Windows receives its sample from a read-only ISO. The agent connects from the host over the preconfigured SSH route and verifies guest access before inspecting.
  4. Perform bounded triageThe host-side agent reads metadata and source, checks hashes and applicable syntax, and records evidence. It does not execute the sample; its report distinguishes observed facts from unknowns.
  5. Use the report as the completion signalOnly a fresh report attributable to the active sample triggers shutdown and cleanup. The manager archives it, clears staged input, removes the disposable overlay, and records the completed hash in SQLite before moving on.
Why keep the agent on the host? The guest stays a small analysis environment. Reasoning, report assembly, and SSH credentials remain outside the malware VM.

What Part One validated

The first batch exercised both guest routes with three cases: a Linux ransomware script, a password-protected Linux archive, and a benign Windows routing fixture. The daemon archived a report for each and left no sample staged or VM running.

All three reviews were static; no payload was executed. The Windows fixture was read from its read-only volume and parsed without running it. These results validate the sample-to-report lifecycle—not a claim of full dynamic malware analysis.

Safety boundary: disposable overlays protect the installed base disks; restricted networking limits guest egress; samples are treated as untrusted input.
