Advanced Red-Team Framework

The component set for a controlled red-team operations hub: a custom H.264 encoder with hardware acceleration, a shared chat bus for operators, a lazy-loading file manager backed by SQLite, an event viewer, and a terminal CLI manager that bridges forkpty on Linux to named pipes on Windows. Native architecture: implants written in C/C++, server in C, operator GUI and service in C#.

Series: Advanced red-team implant Focus: Operator tooling and implant architecture Status: Components defined · architecture review

1. Architecture: C/C++ implants, C server, C# GUI + service

The framework is split across two native tiers plus a managed shell. The implant tier is authored in C/C++ for low-overhead, cross-platform operation: each implant is a thin process that talks to the host service over a local channel. The server is a standalone C binary that brokers connections, owns the SQLite hub, and routes operator commands. The operator surface is a C# GUI (for interactive control) and a C# Windows service (for unattended background sessions), both sharing a small C shim for socket/pipe compatibility.

implants
C/C++ — pure native, cross-platform, zero runtime dependency outside the OS
Server
C — single binary, owns SQLite hub and command routing
Operator GUI
C# — interactive control surface (Windows / cross-platform host)
Background service
C# — unattended implant/session management on Windows
Compatibility shim
C — isolates the platform differences (named pipes vs. Unix sockets) from the C# layer

2. dxgi + custom H.264 encoder for hardware acceleration

The capture layer is built on DirectX Graphics Infrastructure (DXGI), wiring a custom H.264 encoder to the GPU's hardware encode path. The encoder is hand-tuned for low-latency, high-bitrate-capable streaming from the lab VM: it requests the GPU's hardware encoder, submits B-frames and rate-control hints, and dumps the bitstream to a ring buffer that feeds the file manager. The DXGI pipeline keeps the capture from stalling the implant's main loop and lets the operator record high-quality sessions without saturating the CPU.

Pipeline sketch

  • DXGI adapter enumeration & hardware-encoder capability check
  • Custom H.264 encoder (libx264-style wrapper) bound to the GPU
  • Rate control + B-frame tuning for low-latency capture
  • Ring buffer → file manager (SQLite metadata) delivery

3. Cross-platform implants

Each implant is a C/C++ binary compiled for its target OS. The implant surface exposes a small, versioned protocol: heartbeat, file operations, process listing, screen-capture requests, and chat message fan-out. On Linux, the implant's terminal manager uses forkpty to spawn a pseudo-terminal and relay a PTY over the local channel. On Windows, the same logical terminal is implemented with named pipes, so the operator's C# GUI can talk to the same endpoint regardless of platform.

Terminal manager abstraction

  • Linux: forkpty → PTY slave, master relayed over the local channel
  • Windows: named pipe server/client pair, abstracted behind the same C shim
  • Message envelope: { cmd, payload, seq } — identical wire format on both OSes

4. Chat system for operators

The operator chat is a shared bus: every connected implant forwards its messages to the C server, which fans them out to all subscribed GUI clients. The chat supports per-session channels, timestamped messages, and a lightweight "react" hint set so operators can mark commands as executed or failed without opening a second window. Messages are persisted to the SQLite hub with a chat_messages table, giving a running audit trail of every session.

5. File manager with lazy loading and SQLite

The file manager is a lazy-loading tree of objects kept in SQLite. The parent directory row is fetched eagerly; child entries are fetched on demand as the operator expands a folder. Each row carries a hash and size for integrity verification, and the SQLite hub acts as the single source of truth between the file manager, chat bus, and event viewer. Operations are versioned so the operator can undo a "file captured" action.

6. Event viewer

The event viewer aggregates implant heartbeats, capture events, chat messages, and file operations into a chronological feed. Each event references a session and an implant, and the viewer renders them as a compact timeline with severity color-coding so an operator can see anomalous activity (e.g., a sudden burst of file writes or a failed capture) without leaving the operator surface.

Event feed columns

  • Session / implant / timestamp
  • Type: heartbeat, capture, file_op, chat, error
  • Severity: info, warning, alert
  • Payload snippet + link to SQLite event row

7. Terminal CLI manager with forkpty (Linux) and named pipes (Windows)

The CLI manager is the shared terminal surface. It spawns a PTY via forkpty on Linux, or a named pipe pair on Windows, and multiplexes the implant's output to the C# GUI and the file manager's lazy-loading hub. The manager keeps the PTY in raw mode, applies a small line-decoder, and forwards keystrokes back to the implant. Because both paths speak the same wire format, the C# GUI can present one unified terminal to the operator regardless of host OS.

Linux (forkpty)

  • pid = forkpty(&master, NULL, NULL, NULL);
  • Relay master fd → server channel
  • Keystrokes written to master fd

Windows (named pipes)

  • CreateNamedPipe / ConnectNamedPipe
  • Server side → same C shim as Linux path
  • Single wire format across OSes
